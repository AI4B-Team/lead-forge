Property Object

The property object is the unit of return across the Property Data API. It appears:

In data[] of /search.
As subject.data and inside each comps[].property of /comps. For comp records that are listings rather than assessor records, the object uses a listing shape; see Comp record-type variations.
At the top level of /details/{identifier}, with optional with= include sections appended.

This page documents every field that may appear on the object, the includes available on details, and the listing-shape variants used in comps responses.

Field availability. The object is sparse — fields that have no value on a given record are omitted or null. AI scores and lien-related Leadpipes flags are populated only when the account's territory and entitlements allow.

Raw lookup-code fields​

Each LookupCodes.<X> label is derived from a raw integer or alphanumeric code on the property. The raw codes are also returned at the top level of the property object (air_conditioning_code, basement_code, building_class_code, building_condition_code, building_quality_code, construction_type_code, driveway_code, exterior_walls_code, fireplace_code, floor_cover_code, garage, heat_code, heating_fuel_type_code, interior_walls_code, patio_code, pool_code, porch_code, roof_cover_code, roof_type_code, sewer_code, site_influence_code, style_code, water_code, building_area_ind).

Use the raw codes as opaque keys when building filters or pivots; use the LookupCodes.<X> strings for human-readable display. The code → label mapping for each is on the Enums page.

Mortgages​

A property exposes up to four mortgages across three views:

Concurrent (con_curr_mtg{1,2}_*) — mortgages from the most recent recorded sale.
Open (o_mtg{1..4}_*) — currently outstanding mortgages on the property.
Estimated (mtg{1..4}_estimated_*) — derived balance / rate / payment estimates per slot.

AI scores​

Three AI-derived scores are surfaced on each property. They are populated only inside the account's purchased territories — outside those, the fields are null. They are also nulled to 0 for properties that have sold within the last 60 days, since the underlying model lags the market by ~60 days.

Field	Type	Description
index_90d	integer	AI Retail Score. Predicted likelihood the property is well-suited to a retail (owner-occupant) sale in the near term.
index_wls	integer	AI Wholesale Score. Predicted likelihood the property is well-suited to a wholesale / investor-to-investor transaction.
index_inv	integer	AI Rental Score. Predicted likelihood the property is well-suited to a buy-and-hold rental strategy.

Comp record-type variations​

The comps[].property object on a comps response uses a different field set depending on comps[].record_type.

Comps come from multiple data sources. Comp records may originate from public records (assessor / county data) or MLS listings. Because these sources collect different information, the fields available on each comp vary by record_type — listing-sourced comps generally carry fewer fields than assessor-sourced comps. If your integration requires a consistent field set, use the source filter on /comps to restrict results to a single source type. See Enums → Comp Sources for the full source-to-record_type mapping.

record_type: "ASSESSOR"​

The full property object documented above (assessor / public-record shape).

Date formats​
YYYYMMDD (8-digit string with no separators) — used by deed-record and assessor date fields (recording dates, sale dates, filing dates).
YYYY-MM-DD — used by status / listing date fields.
ISO 8601 with time component — used by some MLS-sourced date fields.
Integer epoch — not used in published responses.
